# Ren'Py 汉化工作台改进计划

## 1. 目标

把现有工具从“功能丰富但依赖用户理解内部流程的脚本界面”，升级为可靠、可解释、可恢复的 Ren'Py 汉化工作台。

优先级固定为：

1. 数据与结果可靠
2. 首次使用和项目导航清楚
3. 校对与修正高效
4. 视觉统一、现代且适合长时间使用

正式支持范围为 Windows 上的英文 Ren'Py 游戏到简体中文；其他语言对作为实验能力。游戏库保留为项目入口，但近期不扩展新的娱乐功能。

## 2. 非目标

- 不在近期建设账号、云同步或多人实时协作。
- 不建设第三方插件市场。
- 不为了视觉改造更换 PySide6。
- 不把整个游戏目录复制一份作为常规备份方式。
- 不承诺所有源语言和目标语言组合都达到相同质量。
- 不用新的外观掩盖尚未解决的数据一致性问题。

## 3. 已确认的现状问题

### P0：数据安全与功能契约

1. 项目工作目录只使用游戏目录名称；不同路径中的同名游戏会共享提取结果、词汇表和译文。
2. 译文编辑器按原文合并记录；修改一句会改写所有相同原文，无法保留不同分支译法。
3. 编辑器和翻译任务都可能整份写入 `translations.json`，存在最后写入者覆盖。
4. 编辑页可能复用重新提取前的旧 `jobs.json`，造成“保存成功但游戏没有变化”。
5. 菜单任务 key 的生成与回填规则不一致，并可能在同一块的多个菜单节点间重复。
6. “应用修改到游戏”不会刷新人名和关系词显示层，与文档和界面承诺不符。
7. 关系词、词汇表和人物关系未保存就离开页面时，内容可能被磁盘旧值静默覆盖。
8. 本地词汇表只作为模型提示，没有冲突检查、结果检查或已有译文失效提示。
9. 提取补充逻辑依赖逐行正则和英文特征判断，对多行字符串、复杂表达式、短文本和非英文源存在盲区。

### P1：交互与可访问性

1. 关系表使用默认单行编辑器，内边距和行高过小，长内容无法清楚编辑。
2. 设置页是很长的单列页面，常用参数、服务连接、高级生成参数和游戏库网络设置混在一起。
3. 保存行为不一致：部分控件立即写入，部分依赖底部保存按钮，部分关闭即保存。
4. 缺少统一的未保存状态、离页保护、撤销和操作历史。
5. 全局焦点轮廓被移除，复选框主要依赖颜色，游戏卡缺少键盘操作。
6. 窄窗口下固定侧栏、工具栏和游戏卡容易拥挤。
7. 页面编号和流水线步骤编号是两套体系，用户容易混淆。

### P2：工程化与交付

1. 没有依赖锁定、统一测试入口或持续集成。
2. 正式测试未覆盖词汇表、译文编辑、主提取链路、菜单 key 和项目迁移。
3. 部分临时测试脚本依赖本机绝对路径，无法稳定复现。
4. 用户仍需安装 Python 和依赖，发布形态不是独立桌面应用。
5. API 密钥和 Cookie 目前以明文配置保存。

## 4. 目标产品结构

### 4.1 全局空间

- **游戏库**：发现、选择、启动和管理本地游戏；可以从游戏创建或打开汉化项目。
- **项目切换器**：在窗口顶部切换当前汉化项目，并显示后台任务状态。
- **应用设置**：主题、服务连接、凭据、翻译预设、游戏库网络服务和更新策略。

启动时优先恢复上次项目；没有项目时进入游戏库。

### 4.2 汉化工作台

1. **项目概览**
   - 当前游戏安装和版本
   - 工作阶段与完成度
   - 翻译工作量和预计费用
   - 阻断问题、待检查项和推荐下一步
   - 最近任务与恢复点
2. **文本与译文**
   - 状态、说话人、原文、译文列表
   - 上下文、来源位置、标签与变量差异
   - 人工译文、候选译文和版本历史
   - “修改此处”与“替换全部匹配项”分离
3. **人物与关系**
   - 表格快速浏览
   - 侧边详情面板编辑关系、证据和长备注
   - 多主视角角色与有限的人物间关系约束
4. **词汇与翻译记忆**
   - 项目词汇表
   - 个人词汇库的选择性导入
   - 冲突、必须使用项和术语 QA
   - 带来源的个人翻译记忆建议
5. **检查中心**
   - 提取候选
   - 关系冲突
   - 术语不一致
   - 标签和变量风险
   - 迁移建议与外部 tl 变更
   - 应用和验证异常
6. **应用与验证**
   - 应用前差异预览
   - 快速检查与事务式应用
   - 完整交付验证
   - 停用汉化、恢复点和应用清单

### 4.3 常用模式与专家模式

常用模式始终显示影响费用、质量、隐私和数据安全的选择。专家模式在相同页面中增加任务 key、来源文件、提取理由、原始响应、上下文预算和诊断操作，不建立第二套流程。

## 5. 核心状态模型

### 5.1 项目身份

- 汉化项目使用稳定 UUID，不以目录名称或绝对路径作为身份。
- 一个项目可以关联多个历史游戏安装，但同一时间只有一个当前安装。
- 游戏库记录和汉化项目是不同实体，通过显式关联连接。
- 目录移动后可以重新定位；不同位置的同名游戏不会自动合并。

### 5.2 文本与译文

每个文本出现位置至少保存：

- 稳定出现位置标识
- 所属游戏版本和来源位置
- 源文本及结构指纹
- 说话人、场景和相邻上下文
- 提取方式与确定/候选状态
- 当前译文及来源（模型、人工、迁移、导入）
- 人工确认状态
- 候选译文版本
- 标签、变量和术语检查结果
- 最近应用基线

人工译文不可被自动过程覆盖。源文本或结构指纹变化后，旧译文成为迁移建议而不是当前译文。

### 5.3 项目完成度

- **可试玩**：没有阻断问题，可以安全应用；允许存在明确标记的未译项和非阻断问题。
- **已检查**：所有待检查项已得到处理。
- **可交付**：在已检查基础上，通过游戏编译、标签、变量和结构完整性验证。

## 6. 分阶段实施

### 阶段 0：建立安全网

#### 0.1 统一开发与测试入口

- 增加依赖清单和锁定策略。
- 建立统一测试命令。
- 在干净环境验证安装和测试。
- 增加持续集成：单元测试、迁移测试和最小静态检查。

验收：全新环境可以按文档一次安装并运行完整测试；测试不依赖开发者机器上的游戏路径。

#### 0.2 合成 Ren'Py 回归游戏

覆盖：

- 普通对白和菜单
- 同一原文的不同分支
- 多个菜单节点
- 动态变量对白
- `init python` 文本
- 多行字符串和复杂表达式
- 标签与插值变量
- ipatch 各种覆盖形式
- 多主角和关系词输入

验收：提取、生成任务、回填、再次提取和应用验证可以端到端自动执行。

### 阶段 1：可靠性基线

#### 1.1 SQLite 项目存储与旧数据迁移

- 建立项目、游戏安装、文本位置、译文、候选、词汇、关系、任务和恢复点表。
- 首次升级扫描现有 `work/`、`library.json` 和 `config.json`。
- 每个旧项目生成迁移预览和备份。
- 无法可靠匹配的内容进入待检查，不静默丢弃。

验收：迁移前后项目数量、译文数量和人工内容可对账；重复执行迁移不会创建重复数据。

#### 1.2 精确文本位置与菜单 key

- 为对白、菜单和 strings 建立一致的出现位置标识。
- 修复菜单 key 生成与回填不一致。
- 同一原文的不同位置可保存不同译文。
- 全局复用只对尚无译文的位置提供候选。

验收：同一英文在不同分支可被独立编辑、翻译和回填；多菜单节点没有 key 冲突。

#### 1.3 单项目单写入任务

- 所有提取、翻译、迁移和应用通过项目任务协调器执行。
- 翻译过程按记录事务提交，不再整份覆盖文件。
- 编辑期间的非冲突草稿可以保存；冲突项进入检查中心。

验收：在翻译运行时编辑其他记录不会丢失；中断进程后已提交批次保持一致。

#### 1.4 统一应用与恢复

- 在暂存区生成 tl、显示层脚本、字体和语言入口。
- 执行快速结构检查后统一替换。
- 建立应用清单和恢复点。
- 失败时不改变当前游戏安装。
- “应用到游戏”覆盖全部项目资产，不再存在关系词未刷新的隐藏例外。

验收：任意阶段模拟失败，游戏目录仍保持应用前状态；停用汉化只撤销工具管理的文件。

#### 1.5 外部 tl 变更

- 保存上次应用基线。
- 应用前检测外部改动。
- 提供逐项比较、导入和明确放弃。

验收：手工修改 tl 后，工具不会无提示覆盖；导入后保留人工来源标记。

### 阶段 2：可解释的工作台

#### 2.1 项目概览与状态驱动流程

- 用阶段和状态替代页面编号。
- 展示阻断问题、待检查项、工作量和唯一推荐下一步。
- 长任务显示真实进度、当前动作和安全停止点。

#### 2.2 检查中心

- 统一各类待检查项。
- 支持按严重级别、来源、人物和文件筛选。
- 批量处理前展示影响范围。
- 阻断问题与普通警告视觉和行为分离。

#### 2.3 安全编辑体验

- 建立共用表格编辑器：合理行高、不透明编辑背景、进入时全选、Enter 提交、Esc 取消。
- 长字段在详情面板编辑。
- 自动保存项目草稿，显示保存状态和历史。
- 后台任务冲突时禁止危险编辑或在结束后安全合并。

#### 2.4 设置重组

- 分离服务连接和翻译预设。
- 分离应用设置和项目设置。
- 按接口与模型、翻译策略、费用与性能、游戏集成、游戏库网络服务组织。
- 在线和本地服务只显示适用字段。
- 保存、撤销和删除行为一致。

### 阶段 3：视觉、校对和质量增强

#### 3.1 新视觉系统

- 不继承现有紫色玻璃拟态。
- 使用中性、低疲劳底色和一个功能性强调色。
- 状态颜色只表达明确语义，不承担装饰作用。
- 优先保证长文本、表格、差异和日志的可读性。
- 建立清楚的字号、间距、边框、焦点和禁用状态规范。
- 支持浅色与深色，但不以渐变或发光作为层级手段。

#### 3.2 人物关系编辑器

- AI 建议显示依据台词、置信度和冲突。
- 支持多个主视角角色。
- 支持少量定向人物间关系约束。
- 人工确认内容不被重新扫描覆盖。

#### 3.3 术语 QA 与翻译记忆

- 词汇表支持推荐和必须使用两种强度。
- 检查大小写、词边界、复数和上下文冲突。
- 不做无人确认的机械替换。
- 跨项目记忆只提供候选，显示来源和上下文。

#### 3.4 费用与隐私预检

- 显示发送目标、远程/本地属性、条目数、上下文范围和估算 token。
- 能获取价格时显示估算费用和异常警告。
- 已缓存、人工译文和本次重译范围明确列出。

### 阶段 4：公开发布能力

- Windows 凭据系统保存密钥和 Cookie。
- 构建包含运行环境的便携版。
- 更新前备份并执行数据迁移预检。
- 提供脱敏诊断包。
- 支持不含游戏和凭据的项目包。
- 游戏库保持兼容并作为项目入口，不在此阶段扩展评分之外的新内容服务。

## 7. 值得新增但原先未显式提出的能力

### 7.1 项目健康检查

在概览中回答：

- 当前安装是否仍存在且版本是否变化
- 提取结果是否过期
- 词汇或关系修改后哪些译文需要重新检查
- 是否存在未应用草稿
- 游戏目录是否有外部改动
- 当前结果为何尚未达到可试玩、已检查或可交付

不使用模糊的单一“健康分”，而是给出可操作的问题数量和下一步。

### 7.2 变更影响分析

修改词汇、关系或翻译预设后，先显示会影响哪些文本；用户可以只重译受影响范围。解决当前“改了词表但缓存完全不变、用户不知道原因”的问题。

### 7.3 应用差异预览

应用前展示将新增、更新和移除的文件，以及译文记录变化数量。专家模式可查看具体 tl 差异。

### 7.4 结果来源追踪

每条译文能够回答：

- 由哪个模型或人工产生
- 使用了哪个翻译预设
- 命中了哪些术语和关系约束
- 是否从旧版本或翻译记忆建议而来
- 最后由谁确认以及何时应用

### 7.5 兼容性画像

创建项目时识别 Ren'Py 版本、脚本可用性、rpa/rpyc 情况、已存在 tl、ipatch 类型和动态文本风险，提前说明哪些能力可以自动完成、哪些需要检查。

### 7.6 一键生成交付报告

生成不包含游戏文本的报告，记录项目版本、已应用文件、未译数量、待检查数量、验证结果和工具版本。便于日后复现和排查。

## 8. 成功指标

### 可靠性

- 同名不同路径项目串数据：0。
- 自动过程覆盖人工译文：0。
- 应用失败留下半完成游戏目录：0。
- 未提示覆盖外部 tl 变更：0。
- 迁移前后项目资产可对账率：100%。

### 可用性

- 新用户不阅读 README 也能创建项目并得到工作量预检。
- 任意页面都能判断草稿是否已保存、是否已应用。
- 用户可以从阻断问题直接到达解决位置。
- 相同原文的单条修改和全局替换不会混淆。

### 工程质量

- 核心流程在干净环境一条命令完成测试。
- 合成回归游戏覆盖主提取、菜单、动态文本、ipatch、迁移和应用。
- 关键数据迁移具有幂等测试和失败恢复测试。
- 发布构建不要求用户预装 Python。

## 9. 第一阶段建议任务顺序

1. 建立依赖、测试入口和合成回归游戏。
2. 定义 SQLite schema、迁移版本和备份格式。
3. 实现稳定项目身份并迁移现有 `work/` 数据。
4. 重建文本出现位置和菜单 key。
5. 引入译文版本、人工保护和候选译文。
6. 建立项目任务协调器，移除整份文件并发写入。
7. 实现暂存、验证、应用清单和失败回滚。
8. 检测并处理外部 tl 变更。
9. 为上述链路补齐自动化测试。
10. 在可靠性验收通过后开始工作台 UI 重组。
