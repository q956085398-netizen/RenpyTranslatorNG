# 规格:Ren'Py 汉化工作台可靠性改造与重组

Status: ready-for-agent
Feature: workbench-revamp
Sources: docs/PRODUCT-IMPROVEMENT-PLAN.md、CONTEXT.md、docs/adr/0001–0005

## Problem Statement

用户(愿意检查关系、词汇和译文、但不直接编辑脚本的进阶玩家)目前无法信任工具的"成功"提示:

- 不同路径下的同名游戏会共用同一个工作目录,提取结果、词汇表和译文互相串用。
- 修改一句译文会改写所有相同原文,不同分支的译法被合并覆盖。
- 翻译运行时仍可编辑缓存,两个写入方最后写入者胜,内容悄悄丢失。
- 重新提取后编辑页沿用旧任务清单,"保存成功但游戏没有变化"。
- "应用修改到游戏"不刷新人名与关系词显示层,与界面承诺不符。
- 修改词汇表后旧译文不变,也没有任何解释;外部改过的 tl 文件会被静默覆盖。
- 关系表输入框太小、编辑时残留旧文字,长内容根本看不清。
- 设置页是一整列混杂的长页面;紫色玻璃拟态视觉长时间校对易疲劳。

根源不是"UI 不够漂亮",而是产品定位、信息架构和核心功能契约没有对齐。

## Solution

把工具升级为可靠、可解释、可恢复的 Ren'Py 汉化工作台:游戏库只作为选择和管理游戏的入口。

- 每个汉化项目拥有稳定身份;译文绑定具体文本出现位置;人工译文永不被自动过程覆盖。
- 编辑自动保存为项目草稿;"应用到游戏"是统一的事务式操作,一次性同步译文、人名与关系词显示层、字体和语言入口,失败可回滚、可停用、可恢复。
- 所有歧义集中进检查中心;项目概览呈现阶段、工作量、待检查项和唯一推荐下一步。
- 完成度分为可试玩 / 已检查 / 可交付,不再只看翻译百分比。
- 设置拆分为应用设置与项目设置,服务连接与翻译预设分离。
- 视觉转为克制、清晰、适合长时间校对的专业工具风格,放弃现有紫色玻璃拟态。

优先级固定:数据可靠 → 上手清楚 → 校对高效 → 视觉现代。

## User Stories

### 项目身份与数据可靠

1. 作为常用模式用户,我希望同一游戏在不同安装路径下的汉化项目完全隔离,所以提取结果、词汇表和译文不会串用。
2. 作为常用模式用户,我希望目录移动或重命名后项目仍能重新定位到同一汉化项目,所以历史成果不因整理硬盘而丢失。
3. 作为常用模式用户,我希望相同英文原文在不同人物或分支下可以拥有不同译文,所以修改一处不会悄悄改写全部。
4. 作为常用模式用户,我希望"替换全部相同原文"是一个显式的批量操作并先展示影响范围,所以不会误改。
5. 作为常用模式用户,希望之外——我要求:我手工修改或确认过的人工译文永远不会被重新翻译、重新提取或项目迁移自动覆盖。
6. 作为常用模式用户,我希望重译或换模型的结果以候选译文形式与当前译文对比展示,由我决定是否采用,所以校对成果是一等资产。
7. 作为常用模式用户,我希望编辑内容自动保存为项目草稿并显示保存状态,所以切换页面、关窗或崩溃都不丢内容。
8. 作为常用模式用户,我希望"保存草稿"和"应用到游戏"是两个语义明确的动作,所以我能分清"已保存"和"游戏已更新"。
9. 作为常用模式用户,我希望同一项目同时只运行一个修改核心数据的项目任务,翻译期间仍可浏览和非冲突编辑,所以长任务不必冻结整个软件也不互相覆盖。
10. 作为常用模式用户,我希望翻译过程按记录事务提交而不是整份覆盖文件,所以中断进程后已提交批次保持一致。
11. 作为常用模式用户,我希望重新提取后译文编辑页立即使用最新任务清单,所以不再出现"保存成功但游戏没有变化"。
12. 作为常用模式用户,我希望旧版本 JSON 数据在升级时自动迁移并有预览和备份,所以近百条游戏库记录和已付费译文一条不丢。
13. 作为常用模式用户,我希望游戏换新版本目录时,工具识别为可能的新游戏安装,展示差异,并在验证后迁移词汇、关系和仍然匹配的译文,其余作为迁移建议,所以成果能继承又不会错位到新剧情。

### 应用、验证与恢复

14. 作为常用模式用户,我希望"应用到游戏"一次性同步译文、人名与关系词显示层、字体和语言入口并返回任务摘要,所以应用成功就意味着全部生效。
15. 作为常用模式用户,我希望应用采用"暂存生成 → 快速结构检查 → 统一替换"的事务流程,所以任何阶段失败时游戏目录保持应用前状态。
16. 作为常用模式用户,我希望每次应用生成应用清单和恢复点,所以能一键停用汉化或恢复应用前状态,并知道每个文件是谁生成的。
17. 作为常用模式用户,我希望应用前检测我在工具之外对 tl 文件的外部译文变更,允许逐项比较、导入或明确放弃,所以手工修改不会被静默覆盖。
18. 作为常用模式用户,我希望应用后自动执行快速结构检查,标记"可交付"时再执行完整编译、标签、变量和结构验证,所以日常试玩快、正式交付严。
19. 作为常用模式用户,我希望高影响操作(迁移、清缓存、批量替换、应用)前自动创建恢复点并可查看差异后还原,所以误操作可恢复。
20. 作为常用模式用户,我希望项目完成度分为可试玩 / 已检查 / 可交付三档,所以不被单一翻译百分比误导。

### 提取、检查与解释

21. 作为常用模式用户,我希望提取结果分为确定文本和候选文本,所以可疑字符串不会直接产生 API 费用或破坏游戏。
22. 作为常用模式用户,我希望候选文本说明来源文件和判定原因,所以能自行决定采纳或忽略。
23. 作为常用模式用户,我希望提取候选、关系冲突、术语不一致、结构风险、迁移建议、外部译文变更和应用异常集中在一个检查中心,支持按严重级别、来源、人物和文件筛选,所以不用在多个页面间翻找问题。
24. 作为常用模式用户,我希望阻断问题(可能导致崩溃、写错目标、损坏资产)与普通警告在视觉和行为上明确分离,只有阻断问题阻止应用。
25. 作为专家模式用户,我希望看到任务 key、来源文件、提取理由、原始模型响应和上下文预算,所以能诊断"为什么这句没提取""为什么修改没生效"。
26. 作为专家模式用户,我希望专家诊断是常用页面的展开而不是另一套流程,所以两种模式之间没有认知断层。

### 翻译、费用与隐私

27. 作为常用模式用户,我希望付费翻译任务启动前看到将发送条目数、已缓存数、预计批次数、所用模型、上下文范围和可获得时的费用估算,所以费用可控、范围异常能提前发现。
28. 作为常用模式用户,我希望服务连接明确标识远程 / 本地,任务预检显示数据接收方,所以始终知道游戏文本发给了谁。
29. 作为常用模式用户,我希望翻译默认携带说话人、相邻台词、场景标识和相关人物约束作为翻译上下文,并可调整范围看到成本影响,所以称谓与语气更准且费用可控。
30. 作为常用模式用户,我希望修改词汇、关系或翻译预设后,工具先显示受影响的译文范围并允许只重译该范围,所以能理解词表的作用域而不是面对不变的缓存。
31. 作为常用模式用户,我希望"必须使用"的术语未出现在译文时形成待检查项,展示原文、当前译文和建议译法,可单条或批量采用,所以术语一致又不会被机械替换破坏语境。

### 词汇、关系与记忆

32. 作为常用模式用户,我希望项目词汇表与可跨项目复用的个人词汇库分开,导入时显示新增、冲突和覆盖项,所以通用词可复用而人名不互相污染。
33. 作为常用模式用户,我希望词汇表支持 JSON/CSV 导入导出,所以能在项目和机器之间迁移。
34. 作为常用模式用户,我希望从其他项目积累的个人翻译记忆只提供带来源和上下文的候选建议,不自动套用,所以 Mistress、Daddy 这类跨作品含义不同的词不会被错误复用。
35. 作为常用模式用户,我希望关系表单元格行高足够、编辑背景不透明、进入编辑时默认全选、Enter 提交 Esc 取消,所以长内容看得清、改得准。
36. 作为常用模式用户,我希望选中人物后在侧边详情面板编辑长备注、关系约束和冲突,所以复杂信息有足够空间。
37. 作为常用模式用户,我希望支持多个主视角角色和少量定向的人物间关系约束,所以多视角游戏和称谓随说话人变化的情况也能正确翻译。
38. 作为常用模式用户,我希望 AI 关系建议显示依据台词、置信度和冲突信息,且绝不覆盖已人工确认的关系,所以能信任并快速采纳。

### 导航、设置与视觉

39. 作为常用模式用户,我希望启动时恢复上次项目的项目概览,没有项目时进入游戏库,顶部随时切换项目并显示后台任务状态,所以既不被打断也不迷路。
40. 作为常用模式用户,我希望项目概览呈现当前游戏安装与版本、工作阶段、工作量与预计费用、阻断问题、待检查项和唯一推荐下一步,所以随时知道接下来做什么。
41. 作为常用模式用户,我希望项目健康检查能回答安装是否还在、提取是否过期、词表改动影响哪些译文、是否有未应用草稿、游戏目录是否有外部改动,所以得到的是可操作的问题列表而不是模糊分数。
42. 作为常用模式用户,我希望应用前能看到差异预览(新增、更新、移除的文件和译文变化数量),所以对将发生的变化有信心。
43. 作为常用模式用户,我希望每条译文能查看来源(哪个模型或人工、哪个翻译预设、命中哪些术语与关系约束、是否来自迁移或记忆建议、何时确认与应用),所以结果可追溯。
44. 作为常用模式用户,我希望设置分为应用设置与项目设置,并按接口与模型、翻译策略、费用与性能、游戏集成、游戏库网络服务分组,在线和本地服务只显示适用字段,所以切项目不会沿用错误策略。
45. 作为常用模式用户,我希望服务连接与翻译预设分离并可自由组合,所以换服务商不用复制整套配置。
46. 作为常用模式用户,我希望界面是克制、清晰的专业工具风格:中性低疲劳底色、单一功能性强调色、语义化状态色、清晰的字号间距焦点规范、浅色深色双主题,所以长时间校对不疲劳。
47. 作为常用模式用户,我希望保留全局焦点轮廓、键盘可操作的游戏卡和一致的可访问性状态,所以键盘用户不被排除。

### 发布与安全

48. 作为用户,我希望 API 密钥和 Cookie 默认存入系统凭据而不是明文配置,导出方案默认不含密钥,需要时才显式选择包含,所以安全边界合理。
49. 作为用户,我希望可以导出和导入不含游戏本体与凭据的项目包,包含词汇、关系、译文、决策记录和验证元数据,所以能备份、换机或与协作者异步交换。
50. 作为维护者,我希望一键生成脱敏诊断包(去除密钥、Cookie、绝对路径和不必要游戏文本)由用户决定是否分享,所以可排查不泄密。
51. 作为用户,我希望获得自带运行环境的 Windows 便携版,应用内检查新版本,更新前自动备份并迁移数据、由我确认安装,所以不必预装 Python。
52. 作为维护者,我希望创建项目时自动识别 Ren'Py 版本、脚本可用性、rpa/rpyc 情况、已有 tl、ipatch 类型和动态文本风险(兼容性画像),提前知道哪些能自动完成,所以预期一致。

## Implementation Decisions

### 技术栈与结构

- 保留 PySide6;把单体主界面拆分为业务逻辑与界面层,新建项目状态层(存储)、项目任务协调器、应用事务器三个核心模块。
- 游戏库保留并修复为项目入口;核心工作台可靠之前不扩展新的娱乐网站能力。

### 项目状态与身份(ADR-0001、ADR-0004)

- 引入 SQLite 作为项目状态的唯一可信来源:一个应用级注册数据库保存汉化项目、游戏安装关联与项目元数据;每个汉化项目一个独立项目数据库,保存文本出现位置、译文记录、候选译文版本、词汇、关系、项目任务、恢复点和应用清单。分库的目的是项目包导出、迁移和删除都以项目为单位完整进行。
- 汉化项目使用稳定 UUID 作为身份;目录名称与绝对路径只是游戏安装的属性。一个项目可关联多个历史游戏安装,同一时间只有一个当前安装;不同位置的同名游戏绝不自动合并。
- 配置保留可读文件;密钥与 Cookie 迁入 Windows 凭据系统,配置与导出方案只保存引用。
- 旧数据自动迁移:首次升级扫描现有 work/ 目录、library.json 与 config.json,为每个旧项目生成迁移预览和备份后导入;无法可靠匹配的内容进入待检查项,不静默丢弃;迁移幂等,重复执行不产生重复数据。

### 文本与译文(ADR-0003)

- 为对白、菜单和 strings 建立统一且稳定的出现位置标识;修复菜单 key 生成与回填规则不一致的问题,多菜单节点不再冲突。
- 译文记录绑定文本出现位置;相同源文本的不同位置可持有不同译文;全局替换是显式批量操作。
- 人工译文带人工确认状态;模型、重新提取、迁移只能写候选译文,采用必须经用户动作。
- 源文本或结构指纹变化后,旧译文降为迁移建议而不是当前译文。
- 提取结果带确定 / 候选状态与判定原因;候选文本进入检查中心,确认后才进入翻译任务。

### 并发与应用(ADR-0005)

- 项目任务协调器:提取、翻译、迁移、检查、应用都作为项目任务登记,同一项目同时只允许一个修改核心数据的项目任务;翻译按记录事务提交,不再整份覆盖文件;任务期间的非冲突草稿可保存,冲突项进检查中心安全合并。
- 应用事务器:在暂存区生成 tl、显示层脚本、字体和语言入口 → 快速结构检查 → 统一替换 → 写应用清单 → 建恢复点;任何阶段失败保持游戏目录原状。
- 保存上次应用基线;应用前检测外部译文变更,提供逐项比较、导入或明确放弃。
- "应用到游戏"统一覆盖全部项目资产,包括人名与关系词显示层,不存在隐藏例外。

### 关系模型(ADR-0002)

- 以主视角关系为核心,支持多个主视角角色;允许添加少量重要的定向人物间关系约束。
- AI 关系建议携带依据台词、置信度和冲突信息,作为待确认建议,不覆盖已确认关系。

### 设置与服务

- 服务连接(去哪调用、如何认证、哪个模型)与翻译预设(提示词、批量策略、生成参数、质量要求)分离,可自由组合;前者属应用设置,后者可跨项目复用。
- 设置按接口与模型 / 翻译策略 / 费用与性能 / 游戏集成 / 游戏库网络服务分组;应用设置与项目设置分离;常用模式隐藏专家参数,专家模式在同页展开诊断。

### 视觉

- 完全放弃紫色玻璃拟态;中性低疲劳底色 + 单一功能性强调色;状态色只表达语义;优先保证长文本、表格、差异与日志的可读性;浅色深色双主题;不以渐变或发光作层级手段。

### 交付顺序

- 阶段 0:统一依赖与测试入口、合成 Ren'Py 回归游戏。
- 阶段 1:SQLite 存储与迁移、出现位置与菜单 key、单项目单写入任务、事务式应用与恢复、外部 tl 变更。
- 阶段 2:项目概览、检查中心、安全编辑体验、设置重组。
- 阶段 3:新视觉系统、关系编辑器、术语 QA、翻译记忆、费用与隐私预检。
- 阶段 4:凭据系统、便携版、更新迁移、诊断包、项目包。
- 每阶段保持旧数据可迁移、软件可用;可靠性验收通过后才开始 UI 重组。

## Testing Decisions

- 好的测试只断言外部行为(输入文件 → 输出文件 / 状态查询),不断言内部实现细节;重构不破坏测试。
- 沿用现有测试风格:pytest + 临时目录 + 真实文件操作(与现有 textmap、texttags、ipatch 测试同构)。
- 接缝规划(自上而下,优先最高接缝):
  1. **端到端流水线接缝(最高、主接缝)**:合成回归游戏作为输入,走 提取 → 任务生成 → 模拟翻译(stub 服务连接,不产生网络与费用)→ 应用到游戏 → 再次提取 / 结构验证。合成游戏覆盖普通对白与菜单、同一原文不同分支、多菜单节点、动态变量对白、init python 文本、多行字符串与复杂表达式、标签与插值变量、ipatch 各种覆盖形式、多主角与关系词输入。
  2. **项目存储与迁移接缝**:旧格式 JSON 夹具(work/ 四类文件、library.json、config.json)→ 迁移 → 断言项目数、译文数、人工确认位可对账;重复迁移幂等;故障中断后可恢复。
  3. **应用事务接缝**:在暂存、检查、替换各阶段注入失败,断言游戏目录保持应用前状态、应用清单与恢复点正确、停用汉化只撤销工具管理的文件。
- 翻译服务在测试中始终使用本地 stub 服务连接;真实付费服务不进入自动化测试。
- 回归样本:合成游戏随仓库分发;真实游戏仅作本机私有回归,受版权内容不打包进产品。

## Out of Scope

- 账号、云同步、多人实时协作(仅项目包异步交换)。
- 第三方插件市场或插件 SDK 兼容承诺(只建立内部接口边界)。
- 更换 PySide6 技术栈或维护第二套界面。
- Windows 以外平台的正式支持;任意源 / 目标语言组合的正式质量保证(其他语言对仅实验标识)。
- 游戏库评分、版本、封面之外的新娱乐内容服务。
- 复制整个游戏目录作为常规备份方式。
- 无人确认的机械术语替换。
