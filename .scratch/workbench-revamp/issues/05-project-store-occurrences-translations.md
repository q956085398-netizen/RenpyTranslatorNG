# 05: 项目数据库:出现位置与译文记录

**What to build:** 每个汉化项目一个 SQLite 项目库,保存文本出现位置(对白、菜单、strings 使用统一且稳定的标识)、译文记录、人工确认状态、候选译文版本及来源信息。菜单任务 key 的生成与回填规则一致,同一块中的多个菜单节点不再冲突。相同英文原文的不同出现位置可保存不同译文;源文本或结构指纹变化后旧译文降为迁移建议。人工译文不可被自动过程覆盖(ADR-0003、ADR-0004)。

**Blocked by:** 02(合成回归游戏)、03(项目注册库与稳定项目身份)

**Status:** resolved

- [x] 对白、菜单、strings 的出现位置标识统一且在再次提取后保持稳定
- [x] 菜单 key 生成与回填一致,多菜单节点无冲突(合成游戏验证)
- [x] 同一英文在不同分支可独立编辑、独立翻译、独立回填
- [x] 人工确认的译文在重新翻译时保留,新结果只进入候选译文
- [x] 译文记录带来源(模型/人工/迁移/导入)与结构指纹

## Answer

实现（ADR-0003、ADR-0004；测试 `tests/test_project_store.py` 28 项、
`tests/test_tlgen_keys.py` 2 项 + 合成 e2e 新增工单 05 段）：

- **项目库**：`core/project_store.py` —— 每个汉化项目一个 SQLite（
  `work/<项目身份>/project.db`，随 `store_dir` 走，惰性建库）。`occurrences`
  表存文本出现位置（统一标识 + kind + 源文本 + 翻译源文本 + 说话人 + 来源文件 +
  结构指纹 + active）；`translations` 表存译文记录（status=current/candidate/
  suggestion、source=model/human/migration/import、人工确认位、产生时的源文本与
  指纹快照、note），部分唯一索引在库层兜底"一个出现位置至多一条当前译文"。
  每次操作独立短连接，可跨线程。
- **出现位置标识**：沿用任务 key 体系——对白 `<bid>[:sN]`（引擎翻译块标识符），
  菜单字幕与 strings 统一走 `S:<原文>`（工单 02 Answer 确认的现代引擎语义）。
  同步（`sync_occurrences`）幂等：再次提取标识稳定、零变化；源文本或结构指纹
  变化 → 当前译文自动降为**迁移建议**（带说明）；出现位置消失 → 保留历史
  （active=0）并降级，重复同步不重复计数不重复降级；重新出现不自动恢复。
  结构指纹 = sha1(kind|来源文件|说话人|源文本)，行号故意不入指纹（脚本上方
  任意一行增删都会平移行号，会造成全量误降级）；ipatch 补丁内容变化只刷新
  trans_source、不算结构变化（缓存失效由 ipatch 补丁指纹机制负责）。
- **菜单 key 一致性**：`tlgen.build_jobs` 删除按序号编号的 caption 任务路径
  （同一块多菜单节点序号从零重计必然 `bid:cN` 冲突，且真实引擎下不可达、
  回填从不处理），菜单字幕统一经 strings 生成、回填同一套 key。
- **人工译文保护**（ADR-0003）：`record_model_result(s)` 是模型结果唯一入口——
  当前译文已人工确认 → 新结果只进候选；未确认 → 新结果成为当前译文、旧值降为
  候选（版本保留）。`set_human_translation`/`confirm`/`adopt_candidate`（候选与
  迁移建议的采用入口）都是用户动作。清空缓存（`clear_currents`）与补丁失效
  （`drop_currents`）都不动人工确认的译文。
- **重译请求**：`request_retranslation` + translator 的 `retranslate_keys` ——
  被请求的 key 不吃同文去重缓存、单独重发请求；人工确认的当前译文在重译期间
  继续回填，结果到达只进候选。未同步位置的请求登记占位记录，同步补全不计
  结构变化。
- **pipeline 接入**：任务构建时同步出现位置（strings 恒参与同步——
  translate_strings 只是任务范围选择，关闭它不得误降级 strings 译文）；旧
  `translations.json` 一次性导入项目库（`import_currents` 只补空位，绝不覆盖、
  不复活已降级译文）；翻译/重译/试玩回填/估算/修复标签/清空缓存全部改走项目库，
  `translations.json` 转为派生镜像（pystrings 软去重等读取方沿用）。
- **UI**：译文修改页写入经 `set_human_translation`（真人工来源+确认位），分组
  展示语义不变；「清空译文缓存」清项目库未确认记录并保留人工确认项（对话框
  文案同步）。
- **e2e 断言**（合成游戏）：出现位置可对账（occurrences=currents=任务数）、
  标识再次提取稳定、两个分支独立定稿/独立重译/独立回填（tl 内两行各自译文）、
  人工定稿在重译后保持当前+候选到达、源文本改写后旧译文降为迁移建议。

code-review（双轴）处理：库内"缓存"用词统一为译文记录（持久化 note、分节注释、
docstring）；`adopt_candidate` 扩展为迁移建议的采用入口（采用经用户确认后回到
当前译文）；sync 静默刷新 trans_source、占位记录不再污染对账报告；删除无调用方
的 `db_path` 参数；`_store` 改公开 `store()`、`_store_ready` 更名
`_import_legacy_cache`、状态字符串收敛为模块常量、重复的当前译文查询与翻译前奏
提取为 `_current_row`/`_occurrence_records`/`_prepare_translation_run`。

说明与遗留：
- **编辑器按出现位置的 UX（分支独立查看/编辑、候选对比采用、发起重译）属
  09 号票**；本票只把数据层做对（逐 key 记录 + 保护语义），编辑页分组展示仍是
  "同文同显、保存组内同步"的既有交互。
- **source='migration' 的写入方在 04 号票**（旧数据迁移时写迁移来源）；store
  已定义该枚举与迁移建议的消费入口。
- **翻译按记录事务提交属 06 号票**：现 `record_model_results` 在翻译结束后
  一次性入库，进程中断窗口内的结果会随镜像文件在下次导入时以 import 来源补入
  （不丢失，来源标记不精确）。
- 镜像文件在"种子已写、结果未写"的崩溃窗口内缺重译键：库是可信来源，下次
  导入/翻译自然修复，无数据丢失。
- UI 上「清空译文缓存」等按钮沿用既有"译文缓存"叫法作用户术语桥接（工单 02
  已记录的仓库级词汇债务），库与代码内部已统一为"译文记录"。
